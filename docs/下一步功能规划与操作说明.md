### 1.2 对照课程选题要求的差距（关键）

课程指南对题目 2 的定义是：**"开发一个多用户的基于地图功能的游戏软件，用户到指定地点后说出一句指定的'咒语'，就可以打卡成功。每个用户可以给他人设定打卡任务，也可以看到地图上每个地点打卡成功的用户信息。"**

拆成 4 条硬性要求逐条对照：

| 编号 | 指南要求 | 现状 | 差距 |
|---|---|---|---|
| R1 | 多用户的、基于地图功能的**游戏**软件 | 有地图、有用户体系（openid 建档） | 基本达成，但**没有"游戏"要素**（无积分、无排行、无成就、无对抗） |
| R2 | 到指定地点说出指定"咒语"即打卡成功 | 已实现且已联调通过 | ✅ 达成 |
| R3 | **每个用户可以给他人设定打卡任务** | **完全没有** | ❌ 最大缺口，属于题目核心玩法 |
| R4 | **可以看到地图上每个地点打卡成功的用户信息** | **完全没有** | ❌ 第二大缺口，题目明确点名的功能 |

**结论：R3 和 R4 是当前最该补的两件事。** 现在的产品更像一个"单人打卡工具"，而题目要的是"多用户社交化游戏"。这两条不补，期末评审时"符合选题要求"这一项会明显吃亏（最终结果占 20%）。

### 1.3 顺带发现的工程问题（影响后续开发，建议一起处理）

| 编号 | 问题 | 位置 | 影响 |
|---|---|---|---|
| P1 | `users.totalCheckins` 全仓库没有任何累加逻辑，字段恒为 0 | `login` 云函数只写入初值 0 | 一旦做排行榜，这个字段不能用 |

### 3.1 F-01 打卡任务系统（P0，核心）

#### 3.1.1 目标与业务规则

先跟组内把规则定死，再写代码。推荐下面这套最小可用规则：

1. 用户 A 选择地图上任意一个打卡点，写一句话作为**任务标题**（如"帮我去文萃楼喊一嗓子"），设定**截止时间**，可选设定一句**指定咒语**（不填则用点位默认咒语）。
2. A 把任务**指派给某个用户**（通过分享卡片，B 点开即接受；或先做简化版：A 生成任务后得到一个 6 位**任务码**，B 输入任务码接受）。**建议先做"任务码"版本**，实现简单且不依赖好友关系。
3. B 在截止时间前到达该点位、说对咒语，即任务完成；`records` 里对应记录带上 `taskId`。
4. 双方可见任务状态：`pending`（待接受）/ `accepted`（进行中）/ `completed`（已完成）/ `expired`（已过期）。

#### 3.1.2 数据结构：新增 `tasks` 集合

在云开发控制台新建集合 `tasks`，字段设计：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 自动 | 主键 |
| `title` | string | 是 | 任务标题（≤30 字） |
| `desc` | string | 否 | 任务描述（≤100 字） |
| `pointId` | string | 是 | 目标打卡点 `_id` |
| `pointName` | string | 是 | 冗余存储，避免联表 |
| `spell` | string | 是 | 需要念的咒语（默认取点位 `spell`） |
| `radius` | number | 是 | 判定半径（米），默认取点位 `radius` |
| `creatorOpenid` | string | 是 | 创建者 |
| `creatorNickname` | string | 是 | 冗余，便于列表展示 |
| `assigneeOpenid` | string | 否 | 被指派者（未接受时为空） |
| `inviteCode` | string | 是 | 6 位任务码，**需唯一** |
| `status` | string | 是 | `pending` / `accepted` / `completed` / `expired` |
| `deadline` | Date | 是 | 截止时间 |
| `completedAt` | Date | 否 | 完成时间 |
| `recordId` | string | 否 | 完成时对应的 `records._id` |
| `createdAt` | Date | 是 | 用 `db.serverDate()` |

> **约定**：新集合统一用 `createdAt`，同时把 `records.createTime` 这个历史命名在这一轮里**顺手统一**（见 3.10 的兼容方案），否则越往后越乱。

#### 3.1.3 云函数改动：新增 3 个 + 改造 1 个

> 本节只包含 **F-01 任务系统**相关的云函数。F-02 的 `getPointUsers` 在 **3.2.2** 节。

在 `cloudfunctions/` 下新建 3 个目录（`createTask`、`acceptTask`、`listTasks`），每个目录都要有 `index.js`、`package.json`、`config.json`（**直接复制现有 `getPoints` 目录的三个文件改名字最省事**，`package.json` 里依赖保持 `wx-server-sdk` 即可）。第 4 项是改造已有的 `voiceCheckin`，不需要新建目录。

**① `createTask` —— 创建任务**

```js
// cloudfunctions/createTask/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()

// 生成 6 位任务码，重试直到不重复
async function genInviteCode() {
  for (let i = 0; i < 10; i++) {
    const code = String(Math.floor(100000 + Math.random() * 900000))
    const dup = await db.collection('tasks').where({ inviteCode: code }).count()
    if (dup.total === 0) return code
  }
  throw new Error('任务码生成失败，请重试')
}

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext()
  if (!OPENID) return { code: -1, msg: '未登录' }
  const { title, desc = '', pointId, deadline } = event
  if (!title || !pointId || !deadline) return { code: -1, msg: '参数不完整' }
  if (String(title).length > 30) return { code: -1, msg: '任务标题过长' }

  // 1. 取点位信息（咒语 / 半径 / 名称）
  const pRes = await db.collection('points').doc(pointId).get()
  const point = pRes.data
  if (!point) return { code: -1, msg: '打卡点不存在' }

  // 2. 取创建者昵称（冗余存储）
```

### 3.2 F-02 点位打卡用户信息展示（P0）

#### 3.2.1 目标

#### 3.2.2 新增云函数 `getPointUsers`

> 这个云函数虽然属于 F-02，但**和 F-01 的三个函数同属 P0**，要一起建、一起部署。

**关键点：查询必须在云函数里做，且不返回 `openid`**（隐私要求，报告里要写这一点）。用 `db.command.aggregate` 聚合：

```js
// cloudfunctions/getPointUsers/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()
const $ = db.command.aggregate

exports.main = async (event) => {
  const pointId = event.pointId
  if (!pointId) return { code: -1, msg: '缺少 pointId' }

  // 1. 该点位打卡成功的人数（按 openid 去重）
  const aggRes = await db.collection('records').aggregate()
    .match({ pointId, matched: true })
    .group({ _id: '$pointId', userCount: $.addToSet('$openid') })
    .end()
  const userCount = (aggRes.list[0] && aggRes.list[0].userCount.length) || 0

  // 2. 最近 5 条成功记录
  const recRes = await db.collection('records')
    .where({ pointId, matched: true })
    .orderBy('createTime', 'desc')
    .limit(5)
    .get()

  // 3. 按 openid 去重后取用户昵称头像（只返回昵称 + 头像，不返回 openid）
  const openids = []
  const picked = []
  for (const r of recRes.data) {
    if (openids.indexOf(r.openid) > -1) continue
    openids.push(r.openid)
    picked.push(r)
    if (picked.length >= 5) break
  }

  let users = []
  if (openids.length > 0) {
    const uRes = await db.collection('users')
      .where({ openid: db.command.in(openids) })
      .field({ nickname: true, avatarUrl: true })   // 不取 openid
      .get()
    users = uRes.data
  }

  return {
    code: 0,
    userCount,
    recentUsers: users.map(u => ({ nickname: u.nickname, avatarUrl: u.avatarUrl }))
  }
}
```

> **✅ 已落地（2026-10-14）**，实现与上面示例有 3 处有意差异：
> 1. **人数统计**：示例里 `group({ _id: '$pointId', userCount: $.addToSet('$openid') })` 会把该点位所有 openid 塞进一个数组返回，人多时会顶到聚合内存上限 → 改为 `.group({ _id: '$openid' }).count('n')`，只回传一个数字（语义等价：都是按 openid 去重后计数）。
> 2. **取最近 5 人**：示例 `limit(5)` 之后才去重，同一用户连着打 3 次成功卡，头像墙就凑不满 5 个不同的人 → 改为先取 20 条（`SCAN_LIMIT`）再去重取 5 人（`MAX_USERS`）。
> 3. **头像换链接**：采用下面的**方案 A**，在云函数里用 `cloud.getTempFileURL()` 把 `cloud://` fileID 批量换成 https 临时链接后再返回（`<image>` 不能直接渲染 fileID）；换链接失败时退回空串，前端显示昵称首字占位。
>
> 另外实际实现中 `users` 的 `openid` 也 `field()` 出来了，**仅服务端用于按「最近打卡」顺序重排**，出参一律剥掉 —— 因为 `where(in)` 不保证返回顺序与传入数组一致。U-05「返回体不含 openid」的结论不变。

### 3.3 F-03 积分与排行榜（P1）

#### 3.3.1 积分规则（建议）

| 行为 | 积分 |
|---|---|
| 成功打卡一次 | +10 |
| 完成别人指派的任务 | 额外 +20 |
| 发布任务被完成 | +5（鼓励做任务发布者） |
| 连续打卡第 n 天（n≥2） | +5 × min(n, 5) |

#### 3.3.2 实现方式（避免 P1 的坑）

**不要在 `users` 上做累加计数**（现有 `totalCheckins` 恒为 0 就是前车之鉴）。推荐**实时聚合**：

```js
// 方案：新增 cloudfunctions/getRanking/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()
const $ = db.command.aggregate

exports.main = async (event) => {
  const type = event.type || 'user'   // user 积分榜 / point 点位热度榜

  if (type === 'point') {
    // 点位热度：每个点位成功打卡的独立用户数 + 总次数
    const res = await db.collection('records').aggregate()
      .match({ matched: true })
      .group({
        _id: '$pointId',
        pointName: $.first('$pointName'),
        times: $.sum(1),
        userCount: $.addToSet('$openid')
      })
      .sort({ times: -1 })
      .limit(20)
      .end()
    return {
      code: 0,
      list: res.list.map(i => ({ pointId: i._id, pointName: i.pointName, times: i.times, userCount: i.userCount.length }))
    }
  }

  // 用户榜：独立打卡点位数 + 成功次数
  const res = await db.collection('records').aggregate()
    .match({ matched: true })
    .group({
      _id: '$openid',
      successTimes: $.sum(1),
      points: $.addToSet('$pointId')
    })
    .sort({ successTimes: -1 })
    .limit(20)
    .end()

  // 聚合结果的 _id 就是 openid，需要映射成昵称头像
  const openids = res.list.map(i => i._id)
  const uRes = await db.collection('users')
    .where({ openid: db.command.in(openids) })
    .field({ openid: true, nickname: true, avatarUrl: true })  // 必须带上 openid 才能映射
    .get()

  const userMap = {}
  uRes.data.forEach(u => { userMap[u.openid] = u })

  // ✅ 关键：这里手工拼装返回体，绝不把 openid 带出去
  const list = res.list.map(i => {
    const u = userMap[i._id] || {}
    return {
      nickname: u.nickname || '神秘玩家',
      avatarUrl: u.avatarUrl || '',
      successTimes: i.successTimes,
      pointCount: i.points.length,
      rank: 0   // 前端按数组下标自己编号即可，这里留字段方便扩展
    }
  })
  return { code: 0, list }
}
```

> **踩坑提醒**：`field()` 里如果排除了 `openid`，就没法把聚合结果的 `_id`（其实是 openid）映射到昵称。**正确姿势是查询时带上 `openid` 仅用于内部映射，在拼装返回体时把它删掉。** 报告里要把这一点写成"隐私数据处理说明"。

> **✅ 已落地（2026-10-14）**。与上面示例的差异（都为了让「积分」真的等于 3.3.1 的规则表，而不是只统计打卡次数）：

- **积分按 3.3.1 四条规则实时算、不落库**：`成功打卡 × 10 + 完成他人任务 × 20 + 发布被完成 × 5 + 连续打卡奖励`；排序同分时依次比成功次数、打卡点位数。
- **连续打卡奖励（示例里没有的）**：用 `$dateToString(date: '$createTime', timezone: 'Asia/Shanghai', format: '%Y-%m-%d')` 按「用户 + 自然日」去重拿到 dayKey，再在 JS 里按天扫描算 streak（`+5 × min(n, 5)`，n≥2 起算、断档重置）。这一步包在 `try/catch` 里：万一日期聚合失败，奖励按 0 计并打日志，**不至于整张榜单挂掉**。
- **不用 `addToSet`**：打卡统计改成「按 (openid, pointId) 两阶段聚合」，每组只回传一个次数 —— 理由同 3.2.2（避免把大量 openid 堆进一个数组、顶到聚合内存上限）；总次数与去重后的点位数在 JS 里从「次数 / 组数」累加。

- **多返回一个 `me`**：前端始终能看到自己的名次和积分明细，即使排在前 50 名之外（`OPENID` 只在服务端用于定位自己）。

- `openid` 只用于内部去重 / 排序 / 映射昵称，**出参一律剥掉**（与 3.2.2 同一原则）。
- 纯计算部分抽到 `cloudfunctions/getRanking/lib/points.js`（**不 require `wx-server-sdk`**），并配了本地单测 `tools/test-points.js`（25 条用例，覆盖连续打卡的天数边界：首日不计、断档重置、封顶、跨月跨年、闰年）。跑法：`node tools/test-points.js` —— 这份可以直接写进 D-06「测试用例文档」。

### 3.4 F-04 连续打卡与成就徽章（P1）

**连续打卡（streak）计算**：不要存字段，用聚合临时算。

```js
// 在 getRecords 或新建 getUserStats 云函数里
// 思路：拉取该用户最近 60 天所有 matched 记录，按「自然日」去重后从今天往前数连续天数
```

实现要点：
1. 用 `dayKey`（形如 `2026-10-13`）而不是 Date 比较，避免时区/时分秒干扰；
2. 时区固定按 UTC+8 换算（云函数容器时区是 UTC，**这是常见坑**）；
3. 建议在 `voiceCheckin` 写记录时就存一个 `dayKey` 字段，后续统计不用再换算。

|---|---|

| 马拉松选手 | 连续 7 天打卡 |
| 探险家 | 在 5 个不同点位打卡成功 |
| 任务达人 | 完成 5 个他人指派的任务 |

#### 3.4.1 ✅ 已落地（2026-10-15）与设计差异

**代码已全部完成**：新增云函数 `getBadges`（`index.js` + `lib/badges.js` + `package.json` + `config.json`），新增页面 `pages/badges/`（四件套），`voiceCheckin` 补了 `dayKey` 字段。索引与部署见 3.9.2 / 3.9.4。

落地时对上面的方案做了 **4 处调整**，每处都有具体理由（写报告时正好是「设计决策」素材）：

**① 徽章发放位置：从 `voiceCheckin` 改到独立云函数 `getBadges`（最重要的一处）**

文档建议「发放逻辑放在 `voiceCheckin` 成功分支之后」，但徽章判定要读「该用户全部打卡记录 + 任务统计」，等于每次打卡都往主链路里硬塞 3 次查询。打卡本来就要等讯飞识别 1~3 秒，再叠这些查询会明显变慢；一旦某个查询失败，连打卡本身都可能被拖挂。所以改成 **按需懒判定**：

| 触发时机 | 作用 |
|---|---|
| 打卡成功后前端**异步**调一次 | 有新徽章就弹窗提示（不影响打卡结果，失败静默） |
| 打开徽章页时调一次 | 补发「用户几天没打开 App」期间应得的徽章 |

代价是徽章可能延迟几分钟才显示，收益是打卡主链路零风险。

**② 徽章一律按「历史最长连续」判定，不用「当前连续」**

这是懒判定带来的必然要求，也是最容易写错的地方：用户连续打卡 7 天后，可能过了三四天才打开徽章页 —— 那时「当前连续」早就断成 0 了，如果按当前连续判定，「马拉松选手」**永远发不出去**。所以：

- 徽章判定用 `maxStreak`（历史最长连续）；
- `curStreak`（当前连续）只用于页面展示，且只有在「最后一天是今天或昨天」时才不为 0（昨天打了今天还没打，连续还没断）。
- 测试里专门留了回归用例：`curStreak = 0` 但 `maxStreak = 7` 时，马拉松选手仍然成立。

**③ 统计不用聚合，改成「拉最近 1000 条 + 纯函数计算」**

F-02 / F-03 都用了两阶段聚合来避免把大量数据拉进内存，这里反过来：`getBadges` 单次查询上限 1000 条，且只针对**一个用户**，课程项目的数据量远达不到。好处是计算逻辑能整个抽到 `lib/badges.js`（不依赖 `wx-server-sdk`），**可以脱离云环境做本地单测** —— 覆盖了时区跨日、连续天数边界、8 个徽章的阈值等 81 条用例（`tools/test-badges.js`，可直接写进 D-06 测试用例文档）。真正到数据量大的那天，再改回按天聚合。

**④ `user_badges` 集合没建时降级，而不是报错**

集合是在控制台手工建的，忘了建是很常见的情况。`getBadges` 读写该集合都包了容错：集合不存在时，页面照样能显示 8 个徽章的实时判定结果，只是拿不到「获得时间」、也不会弹「新解锁」（否则每次打开都重弹一遍），并在页面上显示一条提示提醒去建集合。返回值里的 `persist` 字段就是这个状态。

**另外顺带改的**：`voiceCheckin` 写入记录时补上 `dayKey`（UTC+8 的 `YYYY-MM-DD`）。⚠️ 云函数容器时区是 UTC，直接取本地日期会让北京时间 00:00~08:00 的打卡算成前一天，连续天数就错了 —— 这个坑在 D-01 里也值得写一句。历史记录没有 `dayKey`，`lib/badges.js` 的 `dayKeyOf()` 会从 `createTime` 现算，新旧数据都能统计。

**页面**：`pages/badges/badges` —— 顶部连续打卡卡（当前连续 / 最长连续 / 今日状态），下方 8 个徽章的网格（已解锁高亮 + 获得日期，未解锁灰显 + **显示进度**如「2/3 天」，让他知道还差多少），点任意徽章弹出详情（名称 / 条件 / 状态 / 进度）。入口在「我的」页的「成就徽章」。支持下拉刷新、深色模式、字体大小、中英文切换。

**5 处与原始设计不同的决定（都值得写进报告）**

① **咒语长度按「归一化后的有效长度」算，不按原始字符数**。
   规则与 `voiceCheckin` 的 `normalize()` 保持一致：全角转半角 + 去掉空白与常见中英文标点。
   理由：咒语的"长度"应该等于识别时**真正参与比对**的那串字符。否则种子数据里的
   `明德精工，创新包容`（9 个字符、有效长度 8）会被自己的规则判成超限。
   顺手补了一条：归一化后必须**至少含一个汉字/字母/数字**，否则拒绝 —— `@#`、`！！`
   这类纯符号咒语有效长度可能刚好够 2，但语音识别几乎不可能命中，等于建了个永远打不上卡的点位。

② **`getPoints` 出参改成白名单，不回传 `creatorOpenid`**。
   团队约定「对外返回一律白名单字段」。但前端确实需要知道"这个点位是不是我建的"（决定图钉颜色、
   是否显示举报入口），于是把判断放到服务端，只回两个布尔值 `isMine` / `isOfficial`。
   这样前端既能区分来源，又拿不到任何 openid —— 报告里可以当成"最小权限返回"的案例写。

③ **举报用独立 `reports` 集合，不用 points 文档里的内嵌数组**。
   - 独立集合能对 `pointId + reporterOpenid` 建**唯一索引**，并发下也不会重复计票（内嵌数组做不到）；
   - 保留举报原因与时间，便于事后人工复核、也便于发现"谁在滥用举报"；
   - 内嵌数组要"读 → 改 → 写"整个文档，并发会丢举报。
   阈值判定按**不同举报人**去重后计数（`HIDE_THRESHOLD = 3`），同一个人反复举报只算 1 票 ——
   这是防刷的关键。生产环境应该是"自动隐藏 + 人工复核"，课程项目没有后台管理界面，
   所以先做自动隐藏（`points.hidden = true`，之后 `getPoints` 对所有人都不再返回它）。

④ **位置选取做了双路径，`chooseLocation` 失败自动回退**。
   主路径是 `wx.chooseLocation()`（地图上拖图钉、能看到地点名，体验最好）；
   但它依赖小程序后台开通 `chooseLocation` 接口权限，个人主体不一定拿得到。
   失败时自动退回「用当前位置」（`wx.getLocation`，本项目已在用，最稳），并 toast 说明。
   这样**即使 `chooseLocation` 权限没批下来，自建点位功能依然可用**。
   ⚠️ 附带一个坑：`app.json` 的 `requiredPrivateInfos` 必须补上 `"chooseLocation"`，

### 3.6 F-06 打卡记录分页加载（P2，✅ 已落地 2026-10-16）

#### 3.6.1 原始设计（供对照）

`getRecords` 云函数**本来就支持分页**（`event.page`、每页 20、返回 `total`），只是 `pages/records` 从不传 `page` → 永远只显示第一页。原始设计：前端加 `onReachBottom` 触底加载、`records` 累加、底部加「加载中 / 没有更多了」提示，并把 `successCount` 改成服务端统计。

#### 3.6.2 ✅ 已落地与设计差异

落地后**比原始设计多做了四处**：

| 决定 | 为什么 |
|---|---|
| **`hasMore` 改由云函数算**（`page * PAGE_SIZE < total`），前端不再用 `records.length < total` 自己推 | 前端拿到的是**已累加**的数组长度，一旦某页返回条数与 `PAGE_SIZE` 不一致（最后一页、或期间有记录被删），前端推算就会多请求一次空页 |
| **`successTotal` 由云函数全量统计**，前端不再 `records.filter(matched).length` | 这正是下面点出的那个缺陷：分页后按"已加载的页"去数，「打卡成功」会随翻页一路变大。现在统计栏两个数字（`total` + `successTotal`）都来自服务端，翻页恒定 |
| **`getRecords` 出参改白名单**（`pickRecord()`，剥掉 `openid`） | 原先把 `records` 的原始文档整条回传，含 `openid`。虽然是本人的 openid，但与团队「云函数对外只给白名单字段」的约定不符（同 3.12 的隐私整改）。顺带把 `matched` 归一成布尔，老记录缺字段时按未匹配处理 |
| **额外加了下拉刷新**（`enablePullDownRefresh` + `onPullDownRefresh`） | 分页列表光有"加载更多"、没有"回到顶部重载"，用户看到一半想刷新只能退出重进。下拉刷新走 `loadRecords(true, true)`，第二参 `silent = true` 表示不弹全屏 loading（下拉自带转圈，叠两层会打架） |
| **首屏 loading 文案接 i18n** | 原代码 `wx.showLoading({ title: '加载中…' })` 是硬编码中文，英文模式下会露中文 |

**落地文件**：

| 文件 | 改动 |

| `cloudfunctions/getRecords/index.js` | 常量 `PAGE_SIZE = 20`；`pickRecord()` 白名单出参；新增 `successTotal` 与 `hasMore`；补 `OPENID` 空值兜底、`page` 做 `Math.max(1, …)` |

> **不需要新建索引**：分页查询是 `where({openid}).orderBy('createTime','desc')`，走的正是 **IDX-02**（`records: openid + createTime 降序`）；`successTotal` 的 `where({openid, matched:true}).count()` 也能命中 IDX-02 的前缀。IDX-02 属 P0，早已建好。

### 3.7 F-07 打卡结果反馈动效（P2，✅ 已落地 2026-10-17）

#### 3.7.1 原始设计（供对照）

- 成功：整屏撒花 / 徽章放大动画（`wx.createAnimation` 或纯 CSS keyframes），底部弹「打卡成功 +10 分」提示条；

#### 3.7.2 ✅ 已落地与设计差异

- **成功**：整屏撒花（14 片、每次落点随机）+ 居中结果卡 —— 绿色 ✓ 徽章放大弹入、标题「打卡成功」、大字 `+10 分`、「你说的是「…」，相似度 xx%」，2.2s 后自动收起。
- **失败**：录音按钮抖动 0.5s + **从屏幕上沿滑入的红色提示条** + 震动。
- **音效未做**：`wx.createInnerAudioContext` 需要音频文件，仓库里没有合适素材（自带音源要额外下载进包）。文档原本写的是"动效与音效"，本轮只做动效；要补的话加一个 `images/sounds/success.mp3` 即可，代码位置已留在 `showCelebrate()`。

| 决定 | 为什么 |
|---|---|
| **用纯 CSS keyframes，没用 `wx.createAnimation`** | 一次庆祝要同时驱动「14 片撒花各自不同的 left / 延迟 / 时长 / 颜色」+ 一张卡片的弹入，用 `wx.createAnimation` 得维护 15 套实例、逐帧 `export` 再 `setData`，代码量和出错面都大得多。CSS 把 `animation-delay` / `animation-duration` 写进每片的 `style` 就能做到 |
| **失败提示条放在上方（从顶部滑入）**，改动文档原本写的"底部弹提示条" | 底部正是「说咒语」按钮所在：失败后用户八成马上要再念一次，提示条压住按钮就挡住了最要紧的操作。放上方既不挡按钮，也和居中的成功卡片形成"一上一下"的视觉区分 |
| **两个浮层都加 `pointer-events: none`** | 庆祝 / 提示期间用户仍能点按钮（尤其失败后立刻重录）。浮层只负责"显示"，不接管交互 —— 这也是它敢铺满整屏还不加关闭按钮的原因 |
| **⚠️ 浮层是普通 `view` 盖在 `map` 上** | 历史上 `map` 属原生组件、层级最高，普通 `view` 盖不住，必须用 `cover-view`。但基础库 **2.7.0（iOS）/ 2.8.0（Android）起 `map` 已支持同层渲染**，现在（2026）正常客户端都能盖住。若在极老客户端上发现撒花被地图挡掉，把 `.celebrate` / `.feedback-bar` 换成 `cover-view`，或把庆祝动画限制在面板区域即可 —— 记在这里便于答辩时回答"原生组件层级"这类问题 |
| **`+10` 的数字放 JS 常量（`CHECKIN_POINTS`），单位放语言包（`+{n} 分` / `+{n} pts`）** | 数字属业务规则、单位属语言，分开后中英文各自正确，加减积分也不用改文案。⚠️ 它是 `getRanking/lib/points.js` 里 `POINTS.checkin` 的**前端副本**（跨目录不能 require），**改积分规则要两处同改** —— 已由 `tools/check-sync.js` 自动兜住 |
| **「失败」的定义放宽到三种**：念错 / 任务校验失败（`code !== 0`）/ 请求异常（`catch`） | 原先只有"念错"改了 tip，另两种只把报错写进 tip。从用户视角看三种都是"这次打卡没成"，都该给同一种强反馈 |
| **震动包 `try/catch` + 空 `fail`** | 低版本客户端、部分 iOS 机型不支持 `vibrateShort` 或 `type` 参数。震动是锦上添花，绝不能因为它报错打断打卡主流程 |
| **顺带修掉一处硬编码中文**：`if (r.code !== 0)` 里的 `'打卡失败，请重试'` 改为语言包 `failTitleGeneric` | 与 F-06 修的 `'加载中…'` 同类问题：英文模式下会露中文 |

**6 处设计决定**

**① `getDistance` 抽成公共模块 —— 抽的过程逮到一个真 bug**

文档要求的这步本身没有争议，但配套写单测（`tools/test-geo.js`）时立刻暴露一个问题：`formatDistance(null)` 返回了「0 米」。根因是 `Number(null) === 0` 且 `isFinite(0)` 为真 —— **同一个坑在 `hasCoords` 里也存在**（会让「没有定位」被当成赤道上的 `(0,0)`，从而给所有点位算出一个荒唐的距离）。两处都加了显式的 null/空串前置判断，并各留了一条回归用例。

**② 定位失败不阻塞列表**

用户拒绝定位权限时，列表**照样显示全部点位**，只是不显示距离、不做分组。理由：看得到点位是核心功能，看得到距离是增强，不能因为后者失败让前者不可用。反过来说，「算不出距离」也不能等价于「离得近」——`groupByDistance` 里 `distance: null` 一律归到「其他」，否则所有点位都会显示在「附近 500 米内」。

**③ 「回到我的位置」以 `setData(center)` 为主，`moveToLocation()` 为辅**

`map` 的 `longitude/latitude` 绑定在 `data.center` 上，改它地图就会跟过去；`moveToLocation()` 只是让蓝点立刻刷新（部分机型上 `setData` 后 `show-location` 的蓝点不更新）。它失败不影响定位效果，所以包了 `try/catch`，不让一个可选能力把主流程搞挂。

**④ 导航用 `wx.openLocation` 交给微信内置地图**

不需要申请任何地图厂商 key、不用自己算路线规划，成本最低。⚠️ 用户点左上角返回也会走 `fail`（`errMsg` 含 `cancel`），那不算错误 —— 已过滤，不弹提示。

**⑤ 点位列表 → 首页选中，靠 `globalData.pendingPointId` 传一棒**

首页是 **tabBar 页**，`switchTab` 不能带 query，所以没法用 URL 参数。列表页把选中点位的 `_id` 写进 `globalData` 再 `navigateBack`，首页 `applyPendingPoint()` 消费后**立刻清空**（否则下次进首页会又选中一次）。

**时序坑**：`onShow` 触发时 `getPoints` 可能还没返回（`points` 为空），直接查会查不到 —— 所以 `points` 为空就先等着，由 `loadPoints` 成功后再调一次。两条路径都兜住了。

**⑥ 分享按钮用 `open-type="share"`，并 `catchtap` 挡冒泡**

只有原生按钮的 `open-type="share"` 才能让 `onShareAppMessage(res)` 拿到 `res.from === 'button'` 与 `res.target.dataset`，从而分享**具体那一条任务**（路径带任务码）。按钮位于可点击的任务卡片内，加了 `catchtap="noop"` 挡住冒泡 —— 否则点分享会连带触发卡片的「复制任务码」。

**两个交互细节**

- **分享进来的任务码要等登录态确定再处理**：`onLoad` 只把码存进 `this._pendingCode`，真正弹确认框放在 `onShow` 的 `consumePendingCode()` 里。未登录时只 `toast` 提示一次（`_inviteHinted` 防重复），**任务码保留** —— 用户登录后回到本页会再走一遍。
- **处理完立刻清空 `_pendingCode`**，否则每次 `onShow`（例如从发布页返回）都会再弹一次确认框。

> **本轮不需要部署任何云函数** —— 纯前端改动（页面 + `utils/geo.js`），重新编译小程序即可。
>
> 顺带补强了 `tools/check-i18n.js`：新增「扫 wxml 引用的键是否存在」。wxml 里写错一个键名不会报错，运行时那处文案直接空白，只有翻到那个页面、切到那种语言才看得见 —— 现在静态扫一遍就能发现（当前 14 个 wxml 全部通过）。

> **加唯一索引的副作用**：建 IDX-03 之前，如果 `records` 里已经存在同一用户同一点位同一天的多条记录，**建索引会失败**。做法：先在控制台按 `openid + pointId` 查出重复数据删掉，再建索引。同时 `voiceCheckin` 要先补上 `dayKey` 字段写入，否则唯一索引会把 `dayKey` 为 `undefined` 的记录互相冲突。

> **唯一索引（IDX-12 / IDX-13 / IDX-16）同理**：`friends` 的 `userOpenid + friendOpenid` 若库里已有重复的好友关系，`users.inviteCode` 有多条空值/重复值，或 `user_badges` 里同一 `openid + badgeId` 已有多条（旧数据或手工造的测试数据），索引都会建不上 —— 先在控制台查出重复数据清理掉再建。IDX-13 的意义在于：`login` 生成邀请码时只做了 `count` 查重，**并发下仍可能撞码**，唯一索引是最后一道防线（与 `tasks.inviteCode` 同理）；IDX-16 同理，`getBadges` 是「先查有没有 → 没有再 add」，两次并发调用之间仍有窗口，唯一索引兜底（云函数里对写入失败已做忽略处理，不会报错给用户）。

> 可以在控制台按目录手工清一次，或留着（占用量极小）。

### 3.12 隐私整改：好友模块不下发 `openid`（2026-10-16，P1）

#### 3.12.1 问题

`friends` 云函数（同学 `ca2adc0` 引入）有**三处把 `openid` 明文回传给了前端**：

| 位置 | 原出参 |
|---|---|
| `action=list` | 每个好友对象带 `openid` |
| `action=pk` | `me` / `friend` 两个对象都带 `openid` |
| `action=add` | `friend.openid` |

这与团队约定「**云函数对外只给白名单字段，不下发 `openid`**」不一致（`acceptTask`、`getPoints`、`getRanking`、`getPointUsers` 都已按约定剥掉）。更麻烦的是 `pages/pk` 为了 PK 又把 `f.openid` 传回云函数，形成了**「前端传 openid」**的调用形态。

**当下没有可直接利用的漏洞**：本项目所有云函数的身份一律取自 `cloud.getWXContext()`，从不信前端传的身份。但**这种形态本身要掐掉** —— 只要将来某个云函数图省事写成 `event.openid || OPENID`，就等于把「任意账号越权」的入口送出去了；而 `openid` 一旦下发过，就很难再确认哪一版前端还在依赖它。

#### 3.12.2 改法：用「好友关系记录的 `_id`」当对外句柄（`recordId`）

不新增字段、不改集合结构，只把对外标识换成 `friends` 集合里**关系文档的主键 `_id`**：

- 客户端**无权读 `friends` 集合**（权限「仅管理端可读写」），拿到 `recordId` 也关联不到任何用户信息；
- `action=pk` 用 `where({ _id: friendRecordId, userOpenid: OPENID })` **一次查询同时完成「取好友」+「校验归属」** —— 只能 PK 自己的好友，拿别人的 id 也查不出来，比传 `openid` 更难被越权探测；
- `action=list` 出参每项加 `recordId`（`wx:key` 也改用它）；
- `action=add` 出参把 `friend.openid` 换成 `friend.recordId`（`add()` 的返回值里就带 `_id`，无需再查）。

⚠️ `action=pk` 取单条**必须 `where({_id})` 取 `data[0]`，不能用 `doc(id).get()`** —— 后者在记录不存在时会**抛异常**，走不到「你们还不是好友」的兜底分支（云函数通用坑，见 3.11）。

**顺带一起改了 `login`**：它把 `users` 的整份文档（含 `openid`、`phone`）当 `user` 回传，前端还会整份写进 `wx.setStorageSync`。现加 `pickUser()` 白名单，只回 `nickname` / `avatarUrl` / `inviteCode`。已逐处核对前端真正读取的字段（`pages/{index,login,mine,pk}`、`app.js`）就只有这三个，加上前端自己标注的 `source`；`phone` 前端从不展示，没必要落到本地缓存里。

#### 3.12.4 ⚠️ 必须同时重传 2 个云函数（前端也要重新编译）

- 只重新编译前端、不重传云函数 → 新前端传 `friendRecordId`，旧云函数读 `event.friendOpenid` 为空 → **同样提示「缺少好友信息」**。

### 3.13 声控判定缺陷修复：啥也没说也判「打卡成功」（2026-10-17，P0 级缺陷）

> 这是本项目的 **1.3 表 P9**：真机调试时发现「啥也没说，界面显示打卡成功」。不是配置问题、不是讯飞返回异常，是**判定规则写漏了**。

#### 3.13.1 现象与根因

在打卡点范围内按一下「说咒语」，**什么都不说**（或只是环境噪音），界面直接显示「打卡成功」。

根因就是判定通过的那一行：

```js
const matched = sim >= 0.8 || (got.includes(target) || target.includes(got))
```

`got` 是识别结果归一化后的字符串、`target` 是咒语。**当识别结果为空串时 `target.includes('')` 恒为 `true`** —— JS 里任何字符串都「包含」空串。于是「互为包含」这条路把空结果放过去了：

| 识别到 | 归一化后 | 相似度 | `target.includes(got)` | 旧判定 |
|---|---|---|---|---|
| `""`（静音 / 麦克风没录到） | `""` | 0 | **true** | ⚠️ **成功** |
| `"   "`（只有空白） | `""` | 0 | **true** | ⚠️ **成功** |
| `"。"`（全是标点） | `""` | 0 | **true** | ⚠️ **成功** |
| `"明"`（只说咒语里的一个字） | `"明"` | 0.25 | **true** | ⚠️ **成功** |
| `"随便说点啥"` | `"随便说点啥"` | 0 | false | 失败（正常） |

顺带暴露第二个洞：**只说咒语里的一个字也算过**。「互为包含」本意是照顾「说了一句话里含咒语」和「长咒语只念了一段」，但没给较短一方设下限。

**连带影响**（比"显示错了"更严重）：这条 `matched: true` 的假记录会真的写进 `records`，而 **F-03 积分**与 **F-04 连续打卡/徽章**都是从这个集合**实时计算**的 —— 于是白送 10 分、白算一天连续打卡、可能白发一枚徽章。

#### 3.13.2 改法

**① 判定逻辑抽到同目录 `lib/match.js`（纯函数，可本地单测）**

原来 `normalize` / `similarity` / 判定那句都内联在 `voiceCheckin/index.js` 里，而它 `require` 了 `wx-server-sdk` → **本地跑不起来，写不了单测**，这类"规则写错"的问题只能靠真机撞。现在抽到 `cloudfunctions/voiceCheckin/lib/match.js`（不 require 任何依赖），云函数里 `require('./lib/match')` 使用（同 F-03 的 `lib/points.js`、F-04 的 `lib/badges.js`、F-05 的 `lib/validate.js`）：

| 导出 | 作用 |
|---|---|
| `normalize(s)` | 归一化（与前端 `utils/spell.js` 逐字一致，标点表也是） |
| `similarity(a, b)` | 编辑距离相似度 |
| `matchSpell(recognizedText, targetSpell)` | 判定，返回 `{ matched, similarity, gotLen, targetLen, reason }` |
| `REASON` / `SIM_THRESHOLD` / `MIN_CONTAIN_LEN` | 原因枚举与两个阈值 |

**② 两条硬拦截（由 `reason` 驱动）**

- **`NO_SPEECH`**（识别结果归一化后为空）→ **不判成功、也不写记录**，返回 `{ code: 0, matched: false, noSpeech: true }`。前端据此显示「没听清」而不是「咒语没对上」—— 这两件事该做的动作不一样（靠近麦克风 vs 看清咒语）。常理上也不该往记录列表里塞一条空记录污染数据。
- **`INVALID_SPELL`**（咒语归一化后为空 = 脏数据；老数据可能绕过 F-05 的校验存进「纯标点咒语」）→ 返回 `code: -1` 报错。**这条不是多余的**：两侧都为空时 `similarity` 的 `a === b` 分支会返回 **1**，不拦会直接判成功。

**③ 「互为包含」加下限：较短一方 ≥ 2 个有效字**（`MIN_CONTAIN_LEN`）。一条同时堵掉空串和单字。

**④ 顺带的健壮性**：录音文件只有 44 字节（裸 wav 头、一个采样点都没有）时**跳过讯飞**，直接按「没听清」处理 —— 省一次 WebSocket 往返，也避免拿空音频去撞讯飞的报错。

**⑤ `normalize` 补上 `null` 兜底**，现在它与前端 `utils/spell.js`、`createPoint/lib/validate.js` **三处逐字一致**（旧版是 `String(s)`，`null` 会变成字符串 `"null"`）。顺带说一句：三份拷贝里的引号过滤项是 **ASCII 直引号**（U+0022/U+0027），不是中文弯引号 —— 视觉上极易抄错（本次抽 `lib/match.js` 时就错了一次，被 `check-sync` 逮住），这条已写进 `lib/match.js` 的注释与 `check-sync.js` 的第 1 节。

#### 3.13.5 修复前产生的脏数据要清掉

### 3.14 F-11 录音文件清理：从「文件无限堆积」到「7 天后自动消失」（P2，2026-10-17）

#### 3.14.1 原始设计（供对照）

修 **P5**：每次打卡都会往云存储传一段 wav（`voice/` 目录），`voiceCheckin` 只负责下载识别，**从来没人删**。文件会无限堆积，既占配额也留隐私痕迹（用户的声音）。

原计划（3.9.5 步骤 3）：控制台新建触发式云函数 `cleanVoice`，配定时触发器，**每月**清理 7 天前的 `voice/` 文件。

#### 3.14.2 ✅ 已落地与设计差异

| 决定 | 为什么 |
|---|---|
| ① **不能"列目录"，改成「记录 → 文件」反查** | 微信云开发的 `wx-server-sdk` 只有 `uploadFile`/`downloadFile`/`deleteFile`/`getTempFileURL`，**没有列文件的 API**，「遍历 `voice/` 目录」根本写不出来。所以 `voiceCheckin` 写记录时把 `fileID` 一起存进 `records`，`cleanVoice` 反过来查记录拿文件句柄，删完把 `fileID` 清成 `''` 当"已处理"标记。 |
| ② **从"每月一次"改成"每天 04:00"** | 保留期是 7 天，每月才跑一次意味着文件最长会存到 37 天；而函数本身**幂等**（多跑不会多删）、又做了单次上限，每天跑反而最省心，也更容易在演示时"当场看到它动"。 |
| ③ **单次有上限：最多扫 500 条记录、每批删 50 个** | `cloud.deleteFile` 的 `fileList` 上限就是 50，超了整批失败；云函数默认超时 3~20 秒，一次跑太多会中断。所以设计成"每次消化一点 + `truncated` 标记还有剩余"，第二天接着追。 |
| ④ **时间判断一律先挡 `0` / `null` / 空串** | `Number(null) === 0`、`Number('') === 0` 且 `isFinite(0)` 为真。如果把 `0` 当合法时间戳，一条 `createTime` 缺失的记录会被当成 **1970 年**，立刻判过期 → **把用户录音删了**。这是本项目第三次踩同一个坑（前两次是 `hasCoords`、`formatDistance`），所以 `lib/clean.js` 的 `toMs()` 里 `0` 与负数一律返回 `null`，单测专门钉了这一组。 |
| ⑤ **「没听清」「咒语脏数据」两条分支当场删文件** | 这两条分支**不写记录**，文件不会被任何 `records` 引用 → `cleanVoice` 反查不到 → 变成永远清不掉的孤儿文件。所以 `voiceCheckin` 里加了个 `dropFile()`：删失败只打日志，绝不影响打卡结果。 |
| ⑥ **带 `dryRun` 开关** | 这个函数唯一的动作是**删用户数据**，第一次上线必须能"只看不删"。控制台「测试」里传 `{"dryRun": true}` 就会返回「将会删几条、跳过几条」而不真删。 |

## 7. 风险与注意事项

| 风险 | 影响 | 对策 |
|---|---|---|
| 讯飞语音识别额度用尽或接口变更 | 打卡功能直接不可用 | ① 在报告里写好"降级方案"：`voiceCheckin` 增加开关，识别服务异常时退化为"录音时长 + 音量阈值"的宽松判定；② 提前确认账号额度 |
| 密钥已进 Git 历史 | 有被人盗用风险 | 轮换密钥 + 改为环境变量（见 3.10） |
| 唯一索引导致写入失败 | 打卡报错但不易定位 | 建索引前先清理重复数据；`voiceCheckin` 捕获写入异常并返回友好提示 |
| 手机号用户与微信用户是两套 `openid` | 同一人在两个登录方式下数据不互通 | 短期：报告里说明；长期：以 `phone` 为业务主键做账号合并（超出课程范围，不建议现在做） |
| 组内 5 人分工不均 | 个人报告质量差异大，影响总分 | 用 RACI 表明确到人，每周同步一次进度；云函数、前端、文档三条线并行 |
| 现场演示时定位不准 / 信号差 | 演示翻车 | 提前踩点；准备"演示模式"：允许评委手动把判定半径临时调大（在云函数里加一个 `DEBUG` 开关，评审后关闭） |
| 期末前才集中补文档 | 文档质量差，15% 丢分 | 每周至少归档一份文档，把"写文档"当开发的一部分 |

## 9. 关于 AI 工具使用（课程硬性要求）

课程指南原文要求：

> "各小组可以使用 AI 工具来协助完成软件开发环节中文档生成和编码工作，但不得使用 AI 工具代替人工完成整个项目，且任何使用了 AI 工具辅助之处均需在文档和报告中清晰说明并标注。"

并且明确：

> "所有环节提交的成果严禁抄袭、代做、主体由 AI 生成等各种形式的学术不端，一经查实，成绩以 0 分计！"

**建议的执行方式**：

1. 在本项目里维护一份 `AI_USAGE.md`，按日期记录：**哪个文件 / 哪段逻辑 / 用了什么工具 / 人工做了哪些修改与验证**；
2. 报告里单设一节「AI 工具使用说明」，把 `AI_USAGE.md` 汇总进去；
3. **务必人工走一遍**：AI 生成或辅助的代码，必须自己读懂、自己真机验证，能在评审时解释每一行为什么这么写。这份文档（含所有代码骨架）属于**参考实现**，直接照抄不修改、不讲清原理，是学术风险；把它当作"技术方案参考 + 自查清单"来用，才是安全且高效的做法；
4. 建议每人对自己负责的模块在个人报告里写明"本人独立完成的部分"与"参考/辅助的部分"。
5. **✅ 作品内也有了声明**：F-12 的「我的 → 关于」页里有一块高亮的「AI 使用说明」（见 3.15），写明了辅助范围与"AI 不参与需求决策、所有代码经人工审阅 + 单测 + 真机验证"。演示时可以直接翻到这一页给评委看，比只写在文档里更难被质疑"没标注"。
