### 1.2 对照课程选题要求的差距（关键）

课程指南对题目 2 的定义是：**"开发一个多用户的基于地图功能的游戏软件，用户到指定地点后说出一句指定的'咒语'，就可以打卡成功。每个用户可以给他人设定打卡任务，也可以看到地图上每个地点打卡成功的用户信息。"**

拆成 4 条硬性要求逐条对照：

| 编号 | 指南要求 | 现状 | 差距 |
|---|---|---|---|
| R1 | 多用户的、基于地图功能的**游戏**软件 | 有地图、有用户体系（openid 建档） | 基本达成，但**没有"游戏"要素**（无积分、无排行、无成就、无对抗） |
| R2 | 到指定地点说出指定"咒语"即打卡成功 | 已实现且已联调通过 | ✅ 达成 |
| R3 | **每个用户可以给他人设定打卡任务** | **完全没有** | ❌ 最大缺口，属于题目核心玩法 |
| R4 | **可以看到地图上每个地点打卡成功的用户信息** | **完全没有** | ❌ 第二大缺口，题目明确点名的功能 |

**结论：R3 和 R4 是当前最该补的两件事。** 现在的产品更像一个"单人打卡工具"，而题目要的是"多用户社交化游戏"。这两条不补，期末评审时"符合选题要求"这一项会明显吃亏（最终结果占 20%）。

### 1.3 顺带发现的工程问题（影响后续开发，建议一起处理）

| 编号 | 问题 | 位置 | 影响 |

### 3.1 F-01 打卡任务系统（P0，核心）

#### 3.1.1 目标与业务规则

先跟组内把规则定死，再写代码。推荐下面这套最小可用规则：

1. 用户 A 选择地图上任意一个打卡点，写一句话作为**任务标题**（如"帮我去文萃楼喊一嗓子"），设定**截止时间**，可选设定一句**指定咒语**（不填则用点位默认咒语）。
2. A 把任务**指派给某个用户**（通过分享卡片，B 点开即接受；或先做简化版：A 生成任务后得到一个 6 位**任务码**，B 输入任务码接受）。**建议先做"任务码"版本**，实现简单且不依赖好友关系。
3. B 在截止时间前到达该点位、说对咒语，即任务完成；`records` 里对应记录带上 `taskId`。
4. 双方可见任务状态：`pending`（待接受）/ `accepted`（进行中）/ `completed`（已完成）/ `expired`（已过期）。

#### 3.1.2 数据结构：新增 `tasks` 集合

在云开发控制台新建集合 `tasks`，字段设计：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 自动 | 主键 |
| `title` | string | 是 | 任务标题（≤30 字） |
| `desc` | string | 否 | 任务描述（≤100 字） |
| `pointId` | string | 是 | 目标打卡点 `_id` |
| `pointName` | string | 是 | 冗余存储，避免联表 |
| `spell` | string | 是 | 需要念的咒语（默认取点位 `spell`） |
| `radius` | number | 是 | 判定半径（米），默认取点位 `radius` |
| `creatorOpenid` | string | 是 | 创建者 |
| `creatorNickname` | string | 是 | 冗余，便于列表展示 |
| `assigneeOpenid` | string | 否 | 被指派者（未接受时为空） |
| `inviteCode` | string | 是 | 6 位任务码，**需唯一** |
| `status` | string | 是 | `pending` / `accepted` / `completed` / `expired` |
| `deadline` | Date | 是 | 截止时间 |
| `completedAt` | Date | 否 | 完成时间 |
| `recordId` | string | 否 | 完成时对应的 `records._id` |
| `createdAt` | Date | 是 | 用 `db.serverDate()` |

> **约定**：新集合统一用 `createdAt`，同时把 `records.createTime` 这个历史命名在这一轮里**顺手统一**（见 3.10 的兼容方案），否则越往后越乱。

**① `createTask` —— 创建任务**

```js
// cloudfunctions/createTask/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()

// 生成 6 位任务码，重试直到不重复
async function genInviteCode() {
  for (let i = 0; i < 10; i++) {
    const code = String(Math.floor(100000 + Math.random() * 900000))
    const dup = await db.collection('tasks').where({ inviteCode: code }).count()
    if (dup.total === 0) return code
  }
  throw new Error('任务码生成失败，请重试')
}

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext()
  if (!OPENID) return { code: -1, msg: '未登录' }
  const { title, desc = '', pointId, deadline } = event
  if (!title || !pointId || !deadline) return { code: -1, msg: '参数不完整' }
  if (String(title).length > 30) return { code: -1, msg: '任务标题过长' }

  // 1. 取点位信息（咒语 / 半径 / 名称）
  const pRes = await db.collection('points').doc(pointId).get()
  const point = pRes.data
  if (!point) return { code: -1, msg: '打卡点不存在' }

  // 2. 取创建者昵称（冗余存储）
  const uRes = await db.collection('users').where({ openid: OPENID }).limit(1).get()
  const creatorNickname = (uRes.data[0] && uRes.data[0].nickname) || '神秘玩家'

  // 3. 写库
  const inviteCode = await genInviteCode()
  const addRes = await db.collection('tasks').add({
    data: {
      title: String(title).slice(0, 30),
      desc: String(desc).slice(0, 100),
      pointId,
      pointName: point.name,
      spell: point.spell,
      radius: point.radius || 50,
      creatorOpenid: OPENID,
      creatorNickname,
      assigneeOpenid: '',
      inviteCode,
      status: 'pending',
      deadline: new Date(deadline),
      createdAt: db.serverDate()
    }
  })
  return { code: 0, taskId: addRes._id, inviteCode }
}
```

**② `acceptTask` —— 凭任务码接受任务**

```js
// cloudfunctions/acceptTask/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext()
  const code = String(event.inviteCode || '').trim()
  if (!code) return { code: -1, msg: '请输入任务码' }

  const res = await db.collection('tasks')
    .where({ inviteCode: code, status: 'pending' }).limit(1).get()
  if (res.data.length === 0) return { code: -1, msg: '任务码无效或任务已被接受' }
  const task = res.data[0]

  if (task.creatorOpenid === OPENID) return { code: -1, msg: '不能接受自己发布的任务' }
  if (new Date(task.deadline) < new Date()) {
    await db.collection('tasks').doc(task._id).update({ data: { status: 'expired' } })
    return { code: -1, msg: '任务已过截止时间' }
  }

  await db.collection('tasks').doc(task._id).update({
    data: { assigneeOpenid: OPENID, status: 'accepted', acceptedAt: db.serverDate() }
  })
  return { code: 0, task }
}
```

**④ 改造 `voiceCheckin` —— 支持带 `taskId` 打卡**

在现有 `voiceCheckin/index.js` 的 `exports.main` 里做三处改动：

```js
// ===== 改动 1：入参多接一个 taskId =====
// 位置：exports.main 里 `const pointId = event.pointId` 的下一行
const taskId = event.taskId || ''

// ===== 改动 2：带 taskId 时用任务里的咒语替代点位默认咒语 =====
// 位置：读完 `point`（第 154-155 行）之后、调用 recognize() 之前
//       放在前面是为了提前拦截非法任务，省掉一次讯飞调用
let targetSpell = point.spell
let task = null
if (taskId) {
  // ⚠️ 必须用 where 查，不能用 doc(taskId).get()
  //    云函数端 doc().get() 查不到记录时会「抛异常」，不是返回 null：
  //    errCode: -1, errMsg: document.get:fail document with _id xxx does not exist
  //    也就是说下面的 if (!task) 永远执行不到，前端只会收到一个函数执行失败的报错。
  //    where 查询空结果返回空数组，才能真正走到友好提示。
  const tRes = await db.collection('tasks').where({ _id: taskId }).get()
  task = tRes.data[0]
  if (!task) return { code: -1, msg: '任务不存在' }
  if (task.status !== 'accepted') return { code: -1, msg: '任务状态异常' }
  if (task.assigneeOpenid !== OPENID) return { code: -1, msg: '这不是指派给你的任务' }
  // 任务必须在指定点位完成：任务写在 A 点，站在 B 点念对咒语也不算过。
  // 前端虽然限制了「同点位才传 taskId」，但前端不可信，云函数才是真正的关卡。
  if (task.pointId !== pointId) return { code: -1, msg: '请在任务指定点位打卡' }
  if (new Date(task.deadline) < new Date()) return { code: -1, msg: '任务已超时' }
  targetSpell = task.spell
}
```

```js
    spell: targetSpell,                 // 原来是 point.spell，改成实际比对用的咒语
    recognizedText: recognizedText,
    similarity: Math.round(sim * 100) / 100,
    matched: matched,
    taskId: taskId || null,             // 新增
    createTime: db.serverDate()
  }
})

// 打卡成功且属于任务打卡 → 把任务置为已完成
if (task && matched) {
  await db.collection('tasks').doc(taskId).update({
    data: {
      status: 'completed',
      completedAt: db.serverDate(),
      recordId: addRes._id              // 对应 tasks 字段表里的 recordId
    }
  })
}
```

#### 3.2.2 新增云函数 `getPointUsers`

> 这个云函数虽然属于 F-02，但**和 F-01 的三个函数同属 P0**，要一起建、一起部署。

**关键点：查询必须在云函数里做，且不返回 `openid`**（隐私要求，报告里要写这一点）。用 `db.command.aggregate` 聚合：

```js
// cloudfunctions/getPointUsers/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()
const $ = db.command.aggregate

exports.main = async (event) => {
  const pointId = event.pointId
  if (!pointId) return { code: -1, msg: '缺少 pointId' }

  // 1. 该点位打卡成功的人数（按 openid 去重）
  const aggRes = await db.collection('records').aggregate()
    .match({ pointId, matched: true })
    .group({ _id: '$pointId', userCount: $.addToSet('$openid') })
    .end()
  const userCount = (aggRes.list[0] && aggRes.list[0].userCount.length) || 0

  // 2. 最近 5 条成功记录
  const recRes = await db.collection('records')
    .where({ pointId, matched: true })
    .orderBy('createTime', 'desc')
    .limit(5)
    .get()

  // 3. 按 openid 去重后取用户昵称头像（只返回昵称 + 头像，不返回 openid）
  const openids = []
  const picked = []
  for (const r of recRes.data) {
    if (openids.indexOf(r.openid) > -1) continue
    openids.push(r.openid)
    picked.push(r)
    if (picked.length >= 5) break
  }

  let users = []
  if (openids.length > 0) {
    const uRes = await db.collection('users')
      .where({ openid: db.command.in(openids) })
      .field({ nickname: true, avatarUrl: true })   // 不取 openid
      .get()
    users = uRes.data
  }

  return {
    code: 0,
    userCount,
    recentUsers: users.map(u => ({ nickname: u.nickname, avatarUrl: u.avatarUrl }))
  }
}
```

### 3.3 F-03 积分与排行榜（P1）

#### 3.3.1 积分规则（建议）

| 行为 | 积分 |
|---|---|

#### 3.3.2 实现方式（避免 P1 的坑）

**不要在 `users` 上做累加计数**（现有 `totalCheckins` 恒为 0 就是前车之鉴）。推荐**实时聚合**：

```js
// 方案：新增 cloudfunctions/getRanking/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()
const $ = db.command.aggregate

exports.main = async (event) => {
  const type = event.type || 'user'   // user 积分榜 / point 点位热度榜

  if (type === 'point') {
    // 点位热度：每个点位成功打卡的独立用户数 + 总次数
    const res = await db.collection('records').aggregate()
      .match({ matched: true })
      .group({
        _id: '$pointId',
        pointName: $.first('$pointName'),
        times: $.sum(1),
        userCount: $.addToSet('$openid')
      })
      .sort({ times: -1 })
      .limit(20)
      .end()
    return {
      code: 0,
      list: res.list.map(i => ({ pointId: i._id, pointName: i.pointName, times: i.times, userCount: i.userCount.length }))
    }
  }

  // 用户榜：独立打卡点位数 + 成功次数
  const res = await db.collection('records').aggregate()
    .match({ matched: true })
    .group({
      _id: '$openid',
      successTimes: $.sum(1),
      points: $.addToSet('$pointId')
    })
    .sort({ successTimes: -1 })
    .limit(20)
    .end()

  // 聚合结果的 _id 就是 openid，需要映射成昵称头像
  const openids = res.list.map(i => i._id)
  const uRes = await db.collection('users')
    .where({ openid: db.command.in(openids) })
    .field({ openid: true, nickname: true, avatarUrl: true })  // 必须带上 openid 才能映射
    .get()

  const userMap = {}
  uRes.data.forEach(u => { userMap[u.openid] = u })

  // ✅ 关键：这里手工拼装返回体，绝不把 openid 带出去
  const list = res.list.map(i => {
    const u = userMap[i._id] || {}
    return {
      nickname: u.nickname || '神秘玩家',
      avatarUrl: u.avatarUrl || '',
      successTimes: i.successTimes,
      pointCount: i.points.length,
      rank: 0   // 前端按数组下标自己编号即可，这里留字段方便扩展
    }
  })
  return { code: 0, list }
}
```

> **踩坑提醒**：`field()` 里如果排除了 `openid`，就没法把聚合结果的 `_id`（其实是 openid）映射到昵称。**正确姿势是查询时带上 `openid` 仅用于内部映射，在拼装返回体时把它删掉。** 报告里要把这一点写成"隐私数据处理说明"。

### 3.6 F-06 打卡记录分页加载（P2，工作量小，建议顺手做）

```js
data: { page: 1, hasMore: true, loadingMore: false }

onLoad() { this.loadRecords(true) },   // true = 重置

onReachBottom() {
  if (!this.data.hasMore || this.data.loadingMore) return
  this.loadRecords(false)
},

loadRecords(reset) {
  const page = reset ? 1 : this.data.page + 1
  this.setData({ loadingMore: !reset })
  wx.cloud.callFunction({ name: 'getRecords', data: { page } }).then(res => {
    const list = (res.result.records || []).map(item => ({ /* 原格式化逻辑 */ }))
    const records = reset ? list : this.data.records.concat(list)
    this.setData({
      records,
      page,
      hasMore: records.length < (res.result.total || 0),
      loadingMore: false,
      loading: false
    })
  })
}
```

> 现在 `getDistance` 函数写在 `pages/index/index.js` 里，属于页面私有。做 F-09 时**必须抽成公共模块**（`utils/geo.js`），否则会复制粘贴出两份不一致的代码——这在报告里属于"代码复用"的负面案例。

### 3.9 云开发控制台操作清单（重点，容易漏）

> 入口：微信开发者工具 → 顶部菜单「云开发」→ 打开云开发控制台。以下操作**都在控制台里手工完成**，代码改了不会自动生效。

#### 3.9.1 数据库集合

| 步骤 | 操作 |
|---|---|
| 1 | 控制台 → 数据库 → 右上角「+」→ 新建集合 `tasks`（F-01）、`user_badges`（F-04，可选） |
| 2 | 检查现有 4 个集合（`users`/`points`/`records`/`sms_codes`）是否都存在，缺哪个补哪个 |
| 3 | **清掉测试脏数据**：`points` 里如果还有早期在北京其他位置拍的点位，删掉；`records` 里的测试记录可保留（F-02 需要数据） |

#### 3.9.2 索引（性能与唯一性，**必做**）

控制台 → 数据库 → 选中集合 → 「索引管理」→ 「新建索引」：

| 编号 | 集合 | 索引字段 | 是否唯一 | 优先级 |
|---|---|---|---|---|
| IDX-01 | `users` | `openid`（升序） | **唯一** | P0 |
| IDX-02 | `records` | `openid` + `createTime`（降序） | 否 | P0 |
| IDX-03 | `records` | `openid` + `pointId` + `dayKey` | **唯一** | P1（根治重复打卡） |
| IDX-04 | `sms_codes` | `phone` + `createdAt`（降序） | 否 | P1 |
| IDX-05 | `users` | `phone` | 否 | P1 |
| IDX-06 | `records` | `pointId` + `openid` | 否 | P1（F-02 聚合用） |
| IDX-07 | `tasks` | `inviteCode` | **唯一** | P0（F-01 必建） |
| IDX-08 | `tasks` | `creatorOpenid` + `createdAt`（降序） | 否 | P0（F-01 必建） |
| IDX-09 | `tasks` | `assigneeOpenid` + `createdAt`（降序） | 否 | P0（F-01 必建） |

> **注意**：`db.command.aggregate` 的 `$group`/`$match` 在数据量大时会用到索引，但更关键的是**普通查询的索引**。数据量小的时候不加索引也能跑，但报告里的"数据库设计"章节需要这些内容。

> **加唯一索引的副作用**：建 IDX-03 之前，如果 `records` 里已经存在同一用户同一点位同一天的多条记录，**建索引会失败**。做法：先在控制台按 `openid + pointId` 查出重复数据删掉，再建索引。同时 `voiceCheckin` 要先补上 `dayKey` 字段写入，否则唯一索引会把 `dayKey` 为 `undefined` 的记录互相冲突。

#### 3.9.3 权限设置

控制台 → 数据库 → 选中集合 → 「权限设置」。

**推荐配置**：

| 集合 | 权限 | 理由 |
|---|---|---|
| `users` | 仅管理端可读写 | 客户端不应直连，用户资料通过 `login` 云函数读写 |
| `points` | 仅管理端可读写 | 通过 `getPoints` / `createPoint` 云函数 |
| `records` | 仅管理端可读写 | 通过 `voiceCheckin` / `getRecords` 云函数 |
| `sms_codes` | 仅管理端可读写 | **必须**，验证码绝不能对客户端可读 |
| `tasks` | 仅管理端可读写 | 全部走云函数 |

> **重要坑**：权限收紧后，客户端如果还在直连数据库，**不会报错，而是静默返回空数组**，极难排查。团队约定：**所有数据访问一律走云函数**。现有代码已经符合这个约定（前端只调 `wx.cloud.callFunction`），但**每次新增功能都要守住这条线**。

#### 3.9.4 云函数部署

| 步骤 | 操作 |
|---|---|
| 1 | 云函数新增/改动后，在开发者工具左侧文件树右键该云函数目录 → 「上传并部署：云端安装依赖」 |
| 2 | `voiceCheckin` 依赖 `ws`，**必须选「云端安装依赖」**，不要选「上传所有文件」（本地没装 node_modules 会漏依赖） |
| 3 | 部署后在控制台 → 云函数 → 选中函数 → 「日志」里确认无报错 |
| 4 | 新增的 4 个云函数（`createTask`/`acceptTask`/`listTasks` 见 3.1.3，`getPointUsers` 见 3.2.2）每个都要单独部署一次；改造过的 `voiceCheckin` 也要**重新部署** |

#### 3.9.5 云存储

| 步骤 | 操作 |
|---|---|
| 1 | 控制台 → 存储 → 确认 `voice/` 目录（录音）和头像目录存在 |
| 2 | 权限：录音和头像**不要设为"所有用户可读"**，用云函数换临时链接（`getTempFileURL`） |
| 3 | F-11 清理：控制台 → 云函数 → 新建触发式云函数 `cleanVoice`，配置**定时触发器**（`config.json` 里写 `triggers`），逻辑为删除 7 天前的 `voice/` 文件 |

`cleanVoice` 的 `config.json` 定时触发器写法：

```json
{
  "triggers": [
    { "name": "cleanVoiceTimer", "type": "timer", "config": "0 0 4 * * * *" }
  ]
}
```

> `0 0 4 * * * *` 表示每天 04:00 执行（云开发定时触发器是 7 位 Cron：秒 分 时 日 月 周 年）。

### 3.11 真机调试与常见报错速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 打卡点加载失败 | `getPoints` 未部署 / 集合权限不对 | 重新「上传并部署：云端安装依赖」；确认 `points` 权限为"仅管理端可读写" |
| 打卡点列表为空但不报错 | 集合权限收紧后客户端直连（静默返回空数组） | 检查是否绕过了云函数直连数据库 |
| 定位失败 `getLocation:fail auth deny` | 未授权位置权限 | `app.json` 里 `permission.scope.userLocation` 与 `requiredPrivateInfos` 已配好；真机上需手动允许，并在设置页提供跳转 `wx.openSetting` |
| 讯飞返回 `10107` | 音频格式不符 / 空录音 | `voiceCheckin` 里已有诊断日志（打印采样率、声道、位深）。确认录音参数为 **16kHz 单声道 wav**（首页 `recorder.start` 已是该配置）；检查录音时长是否过短 |
| 讯飞返回 `10165` / `11200` | 鉴权失败（密钥错误 / 时间偏差） | 检查密钥与系统时间；`getAuthUrl` 用的是 `toUTCString()`，注意云函数容器时间是否准确 |
| 打卡成功但记录页看不到 | `records` 权限 / `openid` 不一致 | 手机号登录和微信登录可能是两个不同 `openid`，会各自只看到自己的记录。这是**已知设计问题**，报告里需说明账号体系局限 |
| 深色模式在某个页面失效 | 该页 `page` 根节点没绑 `{{dark ? 'dark' : ''}}` | 新增页面时**务必**在根 `view` 上照抄这段 class 绑定，并加 `fontScale` 绑定 |
| 新页面跳转 404 | `app.json` 的 `pages` 数组没注册 | 新增页面第一件事就是注册路由 |
